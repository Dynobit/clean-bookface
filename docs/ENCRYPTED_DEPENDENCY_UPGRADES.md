# Encrypted dependency and host-image maintenance

The security signal workflow checks the root and encrypted-client npm locks daily, on relevant pull requests, and by manual dispatch. It includes build dependencies and fails at moderate severity. Dependabot checks both npm directories weekly and proposes updates; repository administrators must also enable GitHub's dependency graph, Dependabot alerts and security updates in repository settings. On 6 October 2026, repository API readback confirmed Dependabot security updates, secret scanning and push protection enabled. A checked-in schedule alone cannot prove that GitHub has dispatched a job.

The same workflow reads the four exact production image pins from `encrypted-host/images.json`, `operations.py` and `recovery.py`, then scans Synapse, PostgreSQL, Caddy and restic with the pinned Anchore Grype action/tool. Discovery reads source text and never imports host modules or runs the images. The ARM64 job matches the qualified image architecture. Mutable, missing and ambiguous pins fail inventory generation. The scanner refreshes its advisory database and refuses a database older than five days. Medium-or-higher findings, including those without fixes, fail the check. Registry, scanner, database or npm failures also fail; they are not evidence that no vulnerability exists.

Results stay in GitHub Actions logs, check statuses and job summaries. This workflow does not send email/Slack/webhook messages, create a new external alert destination, upload member data, change image pins, merge dependency updates or deploy anything. GitHub account notification preferences are outside this source change. The maintainer should review failed and stale/missing checks in the existing GitHub dashboard, assign an owner and record an affected-version assessment. A passing advisory scan covers known database entries for its exact input/time, not application security or absence of unknown vulnerabilities.

Local source qualification on 6 October 2026 passed two immutable-image inventory/refusal tests, YAML parsing, formatting, and root/client type checks. Both complete npm lockfile audits reported zero known advisories. Official Grype 0.120.0 and its fresh 6 October database were SHA-256 verified in private storage; after a direct database download timed out, the same official database was fetched through an existing read-only transport. All four exact ARM64 image filesystems were scanned without suppressions. The initial pins returned Critical/High package-advisory match counts of 0/21 (Caddy), 28/105 (PostgreSQL), 7/42 (restic), and 25/143 (Synapse). These are matches, not unique vulnerabilities or demonstrated exploits. Image checks fail; production security readiness is not established. A local scan does not establish that the GitHub workflow has executed successfully.

The official Caddy 2.11.7 patch and same-version PostgreSQL 17.11 Bookworm rebuild reduced those counts to 0/9 and 6/78 respectively. Both passed isolated ARM64 host/proxy and backup/restore qualification, including signing identity, media hashes, restored login, resource limits and synthetic retention. Remaining PostgreSQL Critical findings include [glibc CVE-2026-5450](https://security-tracker.debian.org/tracker/CVE-2026-5450), [libxml2 CVE-2026-6653](https://security-tracker.debian.org/tracker/CVE-2026-6653) and [SQLite CVE-2025-7458](https://security-tracker.debian.org/tracker/CVE-2025-7458); Debian lists the installed Bookworm packages as vulnerable without a fixed Bookworm version. The PostgreSQL executable links glibc and libxml2. Do not substitute a different database distribution/libc, hide packages, or suppress findings to pass the scan. Same-version package rebuilds must preserve entrypoints and storage semantics and repeat recovery qualification.

## SDK or cryptography-adjacent upgrade

`matrix-js-sdk` 43.0.0 and its Rust/WASM dependency are intentionally pinned. The recipient and signed-content adapters use private SDK internals and reject other versions. Do not remove a version check, add an override or suppress a failed check simply to make a dependency PR green.

1. Read the upstream advisory, release notes and exact source diff. Identify whether browser SDK, WASM, signing, verification, session backup, IndexedDB or key-sharing behavior changes. Record the affected installed version and severity. A signal is not proof of exploitability, and lack of a fix is not permission to ignore it.
2. Work on an isolated branch. Update the dependency and lock together without unrelated upgrades. Inspect the new SDK's room encryptor, actual Room object identity, verified-device policy, Rust machine accessors, key-backup completion semantics and canonical JSON/signature behavior. Update adapters and their explicit version gate only after their new behavior is demonstrated.
3. Run `npm run check`, `npm test` and `npm run build` in both the repository root and `encrypted-client`. Run both all-dependency npm audits. In `encrypted-client`, run `npx --no-install tsx --test tests/legacy-import.integration.ts`. Preserve every privacy/integrity assertion and inspect failures; do not turn failures into skips.
4. Run the disposable browser harness for every admitted suite: invitation/registration, pair verification and sharing, concurrent and large imports, legacy migration, default OPFS cancellation/recovery, identity-recovery failures, social lifecycle, local cleanup, and the focused shared-photo tests. Use fresh private runtimes, real browser crypto, the exact qualified images and the harness's cleanup. Existing evidence is reusable only for unchanged actual inputs and dependencies. Confirm no unintended recipients receive keys, own-user verification is refused, bad events remain isolated, interrupted recovery resumes, and sign-out/closure removes local keys even after failed opens.
5. Repeat the separate reciprocal-home/federation and fenced-restored-standby journeys. Verify signed history, recovery-kit restoration on a clean browser, original archive/media exports and server-artifact plaintext-marker scans using synthetic data. Preserve missing-key, tampered-signature, unexpected-member, unverified-device and downgrade refusals. Run the current keyboard/accessibility acceptance; automation does not replace the outstanding human reviews.
6. Have a second qualified reviewer inspect crypto-adjacent adapter changes and the actual evidence. The project still needs independent human security review before real personal-data readiness can be claimed. A scanner pass or AI review does not supply that acceptance.
7. Prepare an exact reviewed build, asset hashes, client-origin/header checks and rollback plan. Test whether the old client can safely read any upgraded browser database; an irreversible schema migration needs a compatible recovery/unwind plan, not a blind JS rollback. Preserve prior release artifacts. Deployment is a separate authorized action after review; retain the ability to pause admission/sharing if safe upgrading is blocked.

## Host-image upgrade

1. Review each official release/advisory and choose the exact supported architecture digest. Registry availability on another architecture is not qualification. Update only the reviewed pin; imported-image representations remain disposable local qualification inputs, not arbitrary replacements.
2. On disposable hosts, repeat bootstrap, closed admission and expiry, proxy denied-route/forwarded-address tests, capability/memory/PID/log readback, encrypted-media behavior, backup failure/resume, staged deletion/rewrite reconciliation, strict SFTP rejection/transfer and fenced restore. Verify signing identity, member login, actual encrypted media and clean-browser recovery. Run retention preview/apply only against a disposable repository; never use real backups as a test fixture.
3. Qualify the exact generated backup and local-health systemd units on the intended Linux target. Read back failure/staleness behavior, timer catch-up, image limits and disk headroom. A local Docker test does not qualify unattended scheduling or offsite durability.
4. Prepare the reviewed source/image release with a fresh verified backup, independently retained restore credentials, rollback or database migration recovery plan and exact service ownership. Keep the former primary fenced during a takeover. Do not automatically reload a live service from unreviewed shared-tree edits or assume a PostgreSQL downgrade is safe.

For an urgent unresolved vulnerability, keep the issue and affected scope visible in GitHub, restrict affected admission/features through the established reviewed deployment process when necessary, and preserve user recovery/export access where safely possible. Do not silently substitute another SDK, image, provider or deployment target.

The optional [owned Restic security recipe](../encrypted-host/security-images/restic.Dockerfile) preserves the official base, ARM64 platform, application binary, entrypoint and storage format. Its [package manifest](../encrypted-host/security-images/restic-packages.json) locks six official Alpine 3.24 packages by exact version and SHA-256. Obtain each `<package>-<version>.apk` from the manifest's `packageOrigin` into a private directory. Run:

```sh
python3 encrypted-host/build_security_image.py \
  --packages /private/path/packages \
  --receipt /private/path/restic-build-receipt.json \
  --tag clean-bookface-restic-security:reviewed-version
```

The cached base must match the immutable reference. The build checks each package hash, then verifies Alpine signatures with the base image's trusted keys and installs offline with Docker networking disabled. It refuses an official-looking output tag, checks runtime configuration and the Restic binary hash, and records the output image identity, recipe/package manifest hashes and `project-derived-not-official` ownership. The receipt is build evidence, not deployment authorization or recovery qualification. Build timestamps/manifests may vary; always read back the actual output digest. Never relabel a derived digest as an official restic release. The production constant remains the official image until a reviewed owned artifact has been distributed and its exact digest and receipt integrated explicitly; this command neither edits runtime configuration nor deploys.

The 6 October candidate removed all seven Critical matches and reduced High matches from 42 to 11, Medium from 49 to 6, and Low from 15 to 1 (one Unknown remained). Offline package signatures, unchanged binary/configuration, full-data backup verification, signing identity/media/restored-login checks and synthetic retention passed on the derived ARM64 filesystem. Remaining compiled Go dependencies require a separately reviewed source build; package updates do not change them. [OpenSSH CVE-2026-60002](https://security.alpinelinux.org/vuln/CVE-2026-60002) is relevant to the backup client's SFTP transport and is fixed by Alpine 3.24 `10.3_p1-r1`. No remote SFTP, systemd or production capacity qualification is implied. Synapse still needs security rebuild work, including its installed Python dependencies; Debian's [libcurl CVE-2026-10536](https://security-tracker.debian.org/tracker/CVE-2026-10536) has no fixed Trixie package despite an upstream fix. These remaining findings keep the host advisory check failing.
