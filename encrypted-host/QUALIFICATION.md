# Hosting qualification — 5 October 2026

This evidence covers the optional next-release hosting component, not public deployment or browser cryptography.

Official images: Synapse 1.162.0 and PostgreSQL 17.11, ARM64. Registry manifest digests are pinned in `images.json`. The Mac's direct GHCR and Docker Hub requests timed out. An already configured SSH route downloaded the official images on an ARM64 host, then streamed `docker save` into local `docker load`. No network configuration or existing service was changed. Docker's imported manifest representation differed from registry manifests; `imported-images.json` pins those exact local imported images for the local-only qualification option. Production uses the official registry manifests.

Observed checks:

- Bootstrap started an isolated homeserver and PostgreSQL, generated fictional credentials outside source, removed shared-secret registration configuration and issued token-only invitations.
- API readiness passed. Registration advertised token authentication; guest registration returned 403; federation version returned 404; anonymous public-room enumeration was denied.
- Room publication was denied and authenticated user-directory search returned no users.
- Real invited account registration passed; reuse of its consumed token and an expired invitation were rejected.
- `pg_dump` custom-format backup, restic encryption and `restic check --read-data` passed in **6.54 seconds** on the final source (the earlier drill took 7.97 seconds) on the small fictional fixture.
- A separate Compose project and empty database restored in **16.40 seconds** on the final corrected source (the earlier drill took 19.69 seconds). The one-time-key table was cleared before starting Synapse. Three restored member logins and identities worked, and the signing key matched the source.
- The standby was stopped before resuming the primary. They never served the same identity concurrently.
- Python compilation passed for host, qualification and recovery commands.

Failed attempts counted: direct registry requests timed out; an internal-only Docker network did not publish the loopback API in the local Docker environment (fixed with a separate client network while retaining an internal database network); an initial imported-image config-ID lookup did not match Docker's imported manifest IDs (fixed with exact imported manifest pins); the shared-secret-disabled test initially expected GET to disappear, but Synapse intentionally still returns a nonce (corrected to verify registration POST rejection and removed secret); repeated admin logins hit the existing HTTP 429 rate limiter (three failed rechecks while identifying its long retry window, then fixed by sharing one short-lived admin session within each qualification batch). A final fresh bootstrap also correctly refused a loopback port still briefly occupied after cleanup; the rerun used a different free port. The final restore rerun exposed PostgreSQL temporary-initialization-server readiness: a socket probe passed before the temporary server shut down. The health check now requires TCP readiness, which the initialization server does not expose. None of these failures was treated as a passing check or bypassed by weakening admission limits.

Remaining: independent-host/offsite restore, production HTTPS and proxy route qualification, capacity, unattended backup scheduling and restore alerts, independent security review and full production operations. Encrypted-content restoration and a separate cross-home browser journey are now covered below. The local recovery fixture contained small account/configuration state; these timings are not a workload or availability promise. No public DNS, paid account, public deployment, physical standby or zero-downtime claim is included.

## Routine backup, optional SFTP, and automation follow-up

The earlier restore proof deliberately left the primary stopped. The current routine-backup default instead preserves prior service state: after consistent dump/media/config capture, it resumes a previously running primary before upload or verification. `--leave-stopped` is now the explicit restore-drill choice.

A separate disposable installation passed an injected database-dump failure with actual stop/start and subsequent API readiness. A successful routine backup/full-data check took **10.88 seconds** and resumed before upload. An actual wrong-restic-password failure left the primary ready. An explicit `--leave-stopped` backup took **3.22 seconds** and left Synapse stopped. These checks never stopped or changed the browser qualification endpoint on port 18008. The extra local test projects and volumes were removed afterward.

Eight tests in `test_recovery.py` passed: failure cleanup, already-stopped preservation, explicit leave-stopped behavior, generated production restart policy, SSH isolation, hostile argument rejection, symlink/extra-config rejection, and local-only login profile/default preservation. Python compilation and whitespace checks passed. Production-generated services now use `unless-stopped`; local fixtures retain `no`. No existing installation was changed by this generation-policy update.

The SFTP interface was checked against restic 0.19.1's actual bundled OpenSSH executable with networking disabled: effective strict host-key checking, selected identity only, disabled agent use/forwarding, and disabled other forwarding matched the intended settings. There was no pinned SFTP-server image available locally and no remote backup account supplied. **At that checkpoint, an actual SFTP transfer or offsite restore had not been tested.** The later local SFTP proof is recorded below. Local command validation and effective SSH options do not establish that a particular second host works.

The explicit `--test-rate-profile` local fixture completed **32 correct login/logout cycles**; incorrect-password attempts still triggered HTTP 429. Admission/readiness checks also passed on that fixture. Its runtime state recorded `testRateProfile: true`; production rejected the option before filesystem creation, and unflagged local/production configuration retained its original login settings. This profile qualifies repeated browser contexts, not production login-rate policy. The fixture was removed afterward.

## Actual SFTP transport and concurrent-operation protection

A dedicated disposable SFTP receiver passed strict wrong-host-key rejection, repository initialization, backup, full-data verification and fenced restoration. The routine backup resumed the primary and completed in **10.19 seconds**. The isolated standby restored in **17.72 seconds**. Its signing identity matched; all 32,816 bytes of synthetic encrypted media matched SHA-256 and decrypted exactly with the separately retained fixture key. Seven checks passed, and the dedicated primary, standby, receiver containers and database volumes were removed afterward. This transport fixture used synthetic encrypted bytes; the separate larger browser restore above supplies the actual application-content proof.

The receiver ran OpenSSH `1:9.2p1-2+deb12u10` in the pinned official Debian ARM64 image identified by `qualify_sftp.py`. Direct package downloads failed over HTTP and HTTPS. An existing download route fetched 23 official packages (5,245,272 bytes); every SHA-256 matched freshly authenticated apt metadata before offline installation inside the disposable container. No packages were installed on the download host or developer machine. An occupied loopback port was refused. The first correctly pinned SSH attempt also exposed fixture file ownership inherited during copying; OpenSSH StrictModes refused it. Correct root ownership and a dedicated account fixed the fixture. Host-key checking and StrictModes remained enabled.

Recovery commands now take an exclusive per-runtime operation lock before service changes. Restore also locks its new target during reconstruction. A separate process holding the lock prevents another capture from starting. SIGTERM unwinds capture cleanup and attempts to resume a previously running primary; SIGKILL, power loss and Docker failure cannot promise cleanup. The final Python suite passed **12 tests**, including actual process contention and signal cleanup, plus compilation and whitespace checks.

This was a real SFTP transfer between isolated containers on one machine. It does **not** qualify a physical second host, provider credentials, remote retention guarantees, public routing, backup scheduling or a production recovery time.

`qualify_moderation.py` passed actual Synapse report submission/private retrieval, reversible local-account suspension with sending denied, unsuspension with sending allowed, and private verified decision receipts. The final host suite passed **22 tests**; compilation and whitespace checks also passed.

The first Linux attempt failed on the file-ownership error and was completely removed. Their start timestamps changed when the preexisting pilot backup timer independently ran its successful stop/capture/resume cycle during this exercise; its service journal and trigger timestamps explain that readback difference. This is not a claim of uninterrupted pilot service. The required reachability check passed. Exact pinned image caches and private evidence were retained. Still requiring selected-installation acceptance: public DNS/ACME issuance, independent client delivery/control, production capacity/retention and a fenced public-identity takeover. ## Generated federation proxy, discovery and tunnel origin (6 October 2026)

The generated proxy now supports explicitly configured reciprocal peers while keeping the closed default. Preparation verifies agreement among runtime peers, Synapse's whitelist/listener and the advertised client identity before exposing federation/key paths. It generates exact HTTPS `/.well-known/matrix/server` discovery, including delegation to a separate storage hostname on port 443, and denies other identity-host paths. The trusted browser origin must differ from both host origins.

`qualify_operations.py` passed **88 actual route checks** across closed, self-delegated and separately delegated configurations, both with hostname-verified TLS and with the explicit loopback HTTP tunnel origin. These check administration denial, discovery JSON and cache/content headers, forwarded-IP replacement, and preservation of encoded paths, queries, request methods and Authorization. They run the pinned Caddy image with the production capability/security restrictions. An initial reused fixture mount produced a truncated-config parse failure; each variant now uses its own immutable fixture directory. No machine DNS or trusted CA was changed.

`qualify_federation.py --https-proxy` then passed **13 protocol checks** through generated Caddy routes and verified HTTPS discovery, including the actual denied invitation from a non-allowlisted peer, reciprocal opt-in, signed invitation/join, retained encryption state, exact opaque encrypted-event delivery and authenticated remote media. Both homes survived Compose down/up with their fixture topology intact. The fixture CA/leaf certificates now include explicit standards-compliant key-usage and constraints: Python 3.13's strict validator rejected the earlier fixture CA, and verification was kept enabled. A separate attempted run failed closed on an occupied second loopback port and removed its own first home; the passing run prechecked a free pair below the ephemeral port range. All disposable projects, volumes and the shared fixture network were removed.

The explicit tunnel mode publishes Caddy HTTP only on a chosen loopback port. Publicly trusted TLS must be supplied by the selected tunnel; pointing that tunnel directly at Synapse would expose its admin-capable listener and is not this recipe. The pinned Caddy binary requires its bounded `NET_BIND_SERVICE` file capability even when serving a high origin port; production validation caught that requirement and the recipe retains it while dropping other capabilities. The final Python suite passed **24 tests**, with compilation and whitespace checks.

These route/protocol results are not public ACME issuance, independently controlled client delivery or a public-site acceptance claim. [Architecture support](ARCHITECTURE.md) remains Linux ARM64; observing official AMD64 manifests did not qualify an AMD64 installation.

The proxy rejects client API administrative aliases before the general client route, including `api/v1`, `v1`, `r0`, `v3`, `unstable`, and encoded `admin` paths. The six proxy variants passed **130 actual route checks**. The Python suite passed **26 tests**.

A real moderation exercise retrieved selected evidence privately, suspended an account and observed send denial, then unsuspended it and observed send success. All owned disposable projects and volumes were removed.

## Explicit Cloudflare visitor identity (6 October 2026)

The optional `--cloudflare-visitor-ip` transport prevents the local tunnel from collapsing every visitor into one address-based rate limit. The proxy trusts only loopback socket peers and only `CF-Connecting-IP`, using Caddy's native IP parser. Actual pinned-Caddy tests now pass **155 route/forwarding checks**: valid loopback IPv4/IPv6 reach the backend, malformed/missing/list headers fall back to the peer, and nonloopback peers cannot inject either Cloudflare or forwarded-for addresses. Default HTTPS and generic tunnels preserve their original anti-spoof behavior. The Python suite passes **27 tests**. An initial mapping approach emitted an unresolved nested placeholder; the actual backend assertion caught it, and ordered request variables corrected it before deployment.

Cloudflare mode uses Linux host networking with an explicit loopback bind so Docker bridge address translation cannot defeat peer validation. The trust boundary includes Cloudflare and local processes; it is not protection against hostile local users. Public deployment/readback is a separate acceptance step from these disposable proxy checks.
