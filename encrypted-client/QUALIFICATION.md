# Encrypted version: what has actually been tested

Development evidence through 6 October 2026. This is a separate successor to the public v0.1 preview. The independent browser client is deployed for public-route qualification. It does not replace an existing installation and is not ready for personal archives.

## Browser and recovery

The built client ran in isolated Chrome contexts on macOS, using its supplied security headers. The storage fixtures were real Synapse 1.162.0 and PostgreSQL 17.11 ARM64 containers. All accounts, pictures and memories were fictional. Browser recovery kits stayed outside the repository and outside server backups.

The complete ordinary browser run passed five journeys:

- Save a recovery kit and reopen the same account in a clean browser.
- Import privately, compare a friend's identity in two browsers, share selected text, and recover the original archive after signing out and deleting the original device.
- Create an account through a single-use invitation, save its first memory, and recover it in a clean browser.
- Import a valid photo larger than 35 MiB through encrypted pieces of at most 8 MiB under the real home's 25 MiB upload limit. Download the archive and compare the original photo's SHA-256 exactly.
- Refuse key delivery to an unsigned device; preserve a failed publication through reload; explicitly cancel it and sign out. Leaving an unopened recovery screen also works without possessing its kit.

A separate two-home browser journey passed: invitation, acceptance, real matching identity comparison, selected text and photo delivery, and absence of private memories at the recipient. The decoded shared photo had the expected dimensions and pixel values. These were separate homes with separate database and signing identities, on one Docker machine. Container-only test certificates and discovery do not qualify public DNS, HTTPS delegation or an offsite installation.

An earlier combined browser run passed **seven journeys**: the five ordinary flows, separate-home sharing and concurrent first imports. The standby journey is intentionally conditional in that suite. It was run separately against the restored installation and passed; a skipped standby test in the ordinary run is not evidence of recovery.

After disabling unused calling features, six ordinary/concurrent journeys passed again. The cross-home rerun exposed a recreated fixture's missing network attachment, then problems with historical verification requests and unavailable encrypted history in retained test accounts. A fresh pair passed the complete browser journey. Recovery into new browsers on those same homes then passed on the latest source, including matching identity comparison, selected text and photo delivery, private-content exclusion and confirmed key backup before both sign-outs. The final repeated journey took **22.8 seconds** excluding its build.

A forced first-import race also passed: two verified browsers waited at a request barrier, then created two separate archive rooms. Both browsers recovered both memories, and both complete exports retained their exact IDs and text. An initial test clicked download while refresh was still busy and timed out; it now waits for completion. The application also makes its controls inactive during an operation instead of silently accepting a click it cannot handle yet.

## Legacy migration and larger archives (6 October)

An actual v0.1 authenticated account HTTP export was imported through the browser file input, stored on a disposable Synapse home, recovered in a clean browser after deleting the original device, and downloaded again. All four records retained their exact IDs, text, earlier revision, provenance and original-media SHA-256. The final browser journey passed in **19.8 seconds** including runner setup. Requests to the home, its complete PostgreSQL dump, stored media and captured host logs contained none of the planted text markers or original-image bytes. This is a synthetic migration proof, not permission to move an unreviewed personal archive.

The local importer explicitly recognizes `clean-bookface-account/1`, its one declared nested archive, `clean-bookface-archive/1`, and the encrypted client's plaintext portable export. It checks legacy media size/hash and revision identity before returning records. Profiles are preserved as private memories. Account settings, credentials, friendships and permissions are not applied; unimported categories and unreferenced media are disclosed in warnings. The actual-export integration is a required separate command because it needs both server and client dependencies: `npx tsx --test tests/legacy-import.integration.ts` from `encrypted-client`.

The new Facebook path indexes ZIP entry metadata across selected parts and reads media only as needed. It yields batches of at most **96 MiB** of record/media data for sequential encrypted storage. Authenticated archive manifests make retrying completed batches idempotent without downloading all old media. The UI states partial-import progress, supports cancellation and keeps saved parts independently viewable and downloadable. Search over all saved parts decrypts each bounded part locally; no plaintext search is sent to the home.

Seven focused streaming tests passed: on-demand reads, stable cross-part identities and retries, conflicting duplicate paths rejected before the first batch, CRC failure, oversized entries and forged ZIP64 directory metadata, strict JSON/format validation, explicit missing-media warnings, and cancellation after an accepted batch with deterministic restart. The importer bounds aggregate central-directory allocation before zip.js reads it. Limits are **10 GiB** of selected ZIP input and declared expanded data, **64 MiB** per media entry, **16 MiB** per JSON entry, **50,000** logical records, **100,000** ZIP entries and **64** input files. Repeated decoding has a separate 20 GiB work budget. A single record exceeding the batch limit is refused, not silently split or discarded. Unsupported and unreferenced input remains in the original ZIP.

Two distinct capacity measurements passed:

| -------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| Disk-backed importer             | **10,000,000,000 media bytes**, 10,000,194,456-byte ZIP; **597 records / 120 batches**; every ID, text and original-media hash matched; **71.389 s** including fixture creation                                                                                            | Whole Node-process peak RSS **932,200,448 bytes** (about 889 MiB); largest retained batch media **83,886,080 bytes** | Node importer using actual disk ranges; not ten-GiB browser encryption or server recovery                                    |

The ten-GB fixture contained actual stored bytes rather than inflated ZIP size fields or a compressed zero bomb. Node 26.7's `fs.openAsBlob` exposed only 1,410,065,408 bytes of a 10,000,000,000-byte file. A sparse-file boundary diagnostic isolated that 32-bit fixture-API behavior. The successful Node qualification therefore uses an explicit test-only disk-range File adapter; the one-GiB browser proof uses the browser's real file input. Generated files, recovery kits, traces and diagnostic contexts remained outside Git. Owned containers, database volumes, networks and preview servers were removed afterward.

Failed attempts are retained in the evidence: one migration-launch configuration used the wrong installed Playwright path; the new CI harness initially resolved a non-exported Playwright CLI subpath; a streaming test initially expected a different spelling of the correct CRC32 rejection; two test callback typings needed correction; and a ZIP64 test exposed valid sentinel disk fields that the precheck initially rejected. Two ten-GB fixture runs failed at the truncated Node Blob boundary before the explicit range adapter was introduced. The first one-GiB browser run completed import and recovery but omitted the UI's “Show saved imports” step; correcting the test and rerunning the complete journey passed. A concurrent all-client run caught a saved-part search counter bug owned by the main integration; its correction and final project-wide counts are separate from these focused receipts.

## Browser CI admission

The workflow retains the client typecheck, unit tests and build, and explicitly runs the real legacy-export integration after installing both dependency sets. Its encrypted-browser matrix uses the official `ubuntu-24.04-arm` standard runner, pinned ARM64 host images, at most two parallel jobs and one newly bootstrapped local home per test file. It covers the ordinary journey, concurrent imports, migration, social/lifecycle, local cleanup and the one-GiB import. Browser output, host state, generated credentials and recovery kits live under `RUNNER_TEMP`; no artifact upload is configured. Exact owned-host cleanup runs inside the harness and again in an unconditional workflow step.

The harness rejects unexpected skips, flakes and empty runs. Federation and restored-standby qualification remain separate; the conditional standby test is explicitly excluded rather than counted as passing. The local migration harness passed **1/1** with no skips. The sixth-suite harness then reran the complete one-GiB journey and passed **1/1** with no skips in **178.663 seconds** including runner setup; its owned host was destroyed afterward. That repeated run measured 169.648 seconds in the test body and 3,170,975,744 bytes (about 2.95 GiB) peak aggregate Chrome RSS, illustrating run-to-run memory variation. The ownership/cleanup guard tests passed **2/2**. Local harness acceptance is not an observed GitHub Actions result or qualification of a different deployment. GitHub documents the selected ARM64 runner in its [hosted-runner reference](https://docs.github.com/en/actions/reference/runners/github-hosted-runners).

## Second-host recovery

The source fixture held approximately 106 MiB of encrypted content. A stopped-primary capture, encrypted restic backup and full-data check took **6.81 seconds**. A new Compose project with an empty database restored in **19.91 seconds**. The standby and primary never served the same identity simultaneously.

All 20 encrypted media files matched byte for byte by SHA-256, and the server signing identity matched. A fresh browser, supplied with the member's separately retained recovery kit, opened signed memories and the large photos and exported a valid archive. Server backup alone does not recover a lost member key.

These are measurements of one local synthetic fixture. They do not promise an outage duration, continuous availability, offsite protection or a recoverable backup age. Actual strict-host-key SFTP backup and restore also passed a separate local transport fixture. The later two-physical-Linux-host exercise passed **12 checks**, including real scheduled backup, missed-event catch-up, wrong-host-key rejection and fenced restore with exact signing identity and media. Its hosts shared one estate; this does not prove geographic-disaster protection or production takeover. See the exact scope and cleanup in [host qualification](../encrypted-host/QUALIFICATION.md#separate-physical-linux-hosts-and-real-scheduling-6-october-2026).

## Privacy and adversarial checks

The 6 October client typecheck and complete unit run passed **99/99 with zero skips** after the migration, streaming, per-peer blocking and cleanup changes. The earlier 5 October unit and integration baseline passed **65 tests with zero skips**, alongside TypeScript, the built client and formatting checks. It exercises bounded archive parsing, encrypted chunk validation, signed content, hostile membership changes, conflict preservation, recovery and key-backup coverage. Tests use the installed Matrix SDK and Rust crypto where the property depends on those implementations.

- A paused SDK recipient-selection operation rejects an injected third member before any room key is sent. This uses the real SDK queue with a transport spy; it is not a complete malicious-homeserver exercise with three verified browsers.
- The app explicitly disables the SDK's unused voice-call handlers and TURN-server requests. A calling-capable environment test exercises the actual SDK, and browser sign-in checks observe no TURN requests. The app offers no calling or peer-to-peer media feature; this check does not claim to remove every SDK object related to calls.
- An old completed or cancelled identity check cannot clear a different active comparison. Three state-transition tests cover dialog ownership. Sharing a selected memory now waits for confirmed key backup before reporting success, as new text posts already did.
- A fabricated backup encrypted with the public backup key still cannot forge the account's signed content envelope. This uses real crypto, but does not inject the forged session through a live Synapse recovery.
- An isolated Rust machine proves that an earlier backed-up ratchet covers a later local key. Later, unrelated, malformed and mismatched keys are rejected. The live device's key store is not modified by this comparison.
- Independent automated review found recipient-selection races, recovered-sender authentication gaps, conflict handling and recovery-availability defects. Fixes and regression tests are included; this is not an independent human cryptographic audit.
- A 49,000-record archive plus 2,000 new records is refused before upload when the combined limit is known. Concurrent overflow instead produces a clearly partial, bounded view with every authenticated saved batch available separately. Byte limits and slow downloads receive the same availability treatment. Authentication failures still reject; they are never treated as harmless time limits. This is functional regression evidence, not a browser capacity benchmark.

Planted plaintext content markers were absent from the fixture's entire PostgreSQL dump, captured Synapse logs and server files. The scan covered approximately 110 MB of server files. It did not establish that every possible HTTP capture, notification path, crash dump or deployment log is safe. Hosts still see account identifiers, membership, traffic timing and sizes.

The production dependency entries were checked against npm's official bulk-advisory service: 17 packages, zero returned advisory packages. The local `npm audit` request failed at its network endpoint; a separate existing route performed the lock-derived lookup. That is an advisory check, not proof of dependency security. A later correction declared the browser test tools in this package; all 17 production entries stayed identical. Current lock SHA-256: `1af20a320b5fd106668c36d3848cfd27f5af117dc594b6e3dfa0fff26c2d9391`. The 6 October candidate changes only the package version to `0.2.0-preview.1`, not dependency selections. A fresh local `npm audit --omit=dev --audit-level=moderate` succeeded on that lock with zero returned vulnerabilities (18 production entries in npm’s count, including this package).

GitHub's clean runner exposed those missing test dependencies, which had been available through the parent checkout locally. After declaring exact Playwright and sharp development dependencies, an isolated checkout without parent `node_modules` passed a fresh install, TypeScript, all 61 tests and the build. Its ten built files matched the browser-tested files byte for byte. The first isolated fixture omitted the repository's synthetic archive fixture; correcting that snapshot resolved its one failed test. No application behavior or production dependency changed in this packaging correction.

## Limits and failures

The client publisher and its delivery service remain trusted. An operator who can replace the browser app can steal secrets before encryption. Recipients can keep copies. Encryption does not hide the social graph from the homeserver or guarantee erasure.

The client now implements pairwise encrypted comments, reactions, author-owned removal, explicit selected-evidence reports, persistent blocking, account closure and local key cleanup. The social retry outbox is encrypted and browser-local; it is not a portable account-wide outbox. The current four-test social/lifecycle browser set passed after the per-peer block and cleanup-journal fixes: encrypted text/photo conversations, comments and durable retries, reactions and owner removal, selected reports, blocking, third-account HTTP 403 denial, account closure/recovery, same-device reload, fresh invited-account closure, and injected cleanup-journal storage failure with real deactivation and removal of every owned key store/session. Individual tests took 33.6, 1.9, 3.8 and 4.0 seconds; the complete run took about 1.1 minutes including build. Seven lifecycle unit tests also passed, including preservation of canonical per-peer blocks during a forced legacy-list lost update. Account closure does not erase downloaded copies or guarantee host-backup erasure. A final independent source review found that accepting a fresh invitation after blocking and unblocking in the same session retained a transient revocation. Acceptance now clears it only after the new room passes full encryption and membership validation. Two new unit tests cover restored sharing, persistent blocks, hostile joined membership and a new block during joining; the focused content suite passed 48/48 and the full client suite passed 99/99. The actual social browser suite then passed 4/4 without skips or flakes in 85.27 seconds, including block, denied sharing, unblock, a distinct incoming invitation and encrypted sharing/readback in the same client session. Its disposable host was removed afterward.

Facebook imports now stream bounded batches, with the measured scope above. Legacy and native portable exports retain their original bounded import path. These are explicit limits, not unlimited archive capacity. Human security and accessibility reviews, the five-person usability study, independent cryptographic review and selected public-installation acceptance remain unfinished. See [release acceptance](../docs/ENCRYPTION.md).

Failed attempts were counted and corrected: development-server reloads disrupted early tests, so qualification now serves an immutable built snapshot; repeated test logins reached production rate limits, so only disposable fixtures use an explicit test profile; room-version-12 creator permissions and fresh-room crypto timing required integration fixes. A browser test attempted a blob fetch forbidden by the actual CSP; it now verifies the real archive download instead. Neither the CSP nor production admission limits was weakened to make a test pass.

The later cross-home investigation counted five failed runs (one lost fixture network, two identity-comparison cancellations and two unavailable-history failures), one interrupted diagnostic run and one test command that failed before startup. The old retained fixture still contains ciphertext that its recovered browsers cannot decrypt; it has not been declared repaired. Earlier tests discarded browser storage without waiting for received keys to reach backup. The test now signs out through the app's backup confirmation before closing each context. Abrupt device loss before key backup remains a recovery risk. A locally generated SDK cancellation was observed without an application cancel action; its precise cause remains unproven. Successful fresh/recovered-account runs and the dialog fix do not establish that this cancellation has been eliminated.
