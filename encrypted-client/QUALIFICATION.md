The independent browser client now also serves the standalone sample described below; [Releases](https://github.com/Dynobit/clean-bookface/releases) records downloadable versions. ## Legacy migration and larger archives (6 October)

An actual v0.1 authenticated account HTTP export was imported through the browser file input, stored on a disposable Synapse home, recovered in a clean browser after deleting the original device, and downloaded again. All four records retained their exact IDs, text, earlier revision, provenance and original-media SHA-256. The final browser journey passed in **19.8 seconds** including runner setup. Requests to the home, its complete PostgreSQL dump, stored media and captured host logs contained none of the planted text markers or original-image bytes. This is a synthetic migration proof, not permission to move an unreviewed personal archive.

The local importer explicitly recognizes `clean-bookface-account/1`, its one declared nested archive, `clean-bookface-archive/1`, and the encrypted client's plaintext portable export. It checks legacy media size/hash and revision identity before returning records. Profiles are preserved as private memories. Account settings, credentials, friendships and permissions are not applied; unimported categories and unreferenced media are disclosed in warnings. The actual-export integration is a required separate command because it needs both server and client dependencies: `npx tsx --test tests/legacy-import.integration.ts` from `encrypted-client`.

The new Facebook path indexes ZIP entry metadata across selected parts and reads media only as needed. It yields batches of at most **96 MiB** of record/media data for sequential encrypted storage. Authenticated archive manifests make retrying completed batches idempotent without downloading all old media. The UI states partial-import progress, supports cancellation and keeps saved parts independently viewable and downloadable. New saved parts have a signed, encrypted text index, so searching does not fetch their original photos. Older parts and oversized text indexes use bounded original-part reads. The browser decrypts search data locally; no plaintext search is sent to the home. Missing parts make the result explicitly incomplete.

Seven focused streaming tests passed: on-demand reads, stable cross-part identities and retries, conflicting duplicate paths rejected before the first batch, CRC failure, oversized entries and forged ZIP64 directory metadata, strict JSON/format validation, explicit missing-media warnings, and cancellation after an accepted batch with deterministic restart. The importer bounds aggregate central-directory allocation before zip.js reads it. Limits are **10 GiB** of selected ZIP input and declared expanded data, **64 MiB** per media entry, **16 MiB** per JSON entry, **50,000** logical records, **100,000** ZIP entries and **64** input files. Repeated decoding has a separate 20 GiB work budget. A single record exceeding the batch limit is refused, not silently split or discarded. Unsupported and unreferenced input remains in the original ZIP.

## Limits and failures

The client publisher and its delivery service remain trusted. An operator who can replace the browser app can steal secrets before encryption. Recipients can keep copies. Encryption does not hide the social graph from the homeserver or guarantee erasure.

The client now implements pairwise encrypted comments, reactions, author-owned removal, explicit selected-evidence reports, persistent blocking, account closure and local key cleanup. The social retry outbox is browser-local; its encryption key is stored alongside its ciphertext. It is neither a portable account-wide outbox nor protection against a compromised browser profile. The current four-test social/lifecycle browser set passed after the per-peer block and cleanup-journal fixes: encrypted text/photo conversations, comments and durable retries, reactions and owner removal, selected reports, blocking, third-account HTTP 403 denial, account closure/recovery, same-device reload, fresh invited-account closure, and injected cleanup-journal storage failure with real deactivation and removal of every owned key store/session. Individual tests took 33.6, 1.9, 3.8 and 4.0 seconds; the complete run took about 1.1 minutes including build. Seven lifecycle unit tests also passed, including preservation of canonical per-peer blocks during a forced legacy-list lost update. Account closure does not erase downloaded copies or guarantee host-backup erasure. A final independent source review found that accepting a fresh invitation after blocking and unblocking in the same session retained a transient revocation. Acceptance now clears it only after the new room passes full encryption and membership validation. Two new unit tests cover restored sharing, persistent blocks, hostile joined membership and a new block during joining; the focused content suite passed 48/48 and the full client suite passed 99/99. The actual social browser suite then passed 4/4 without skips or flakes in 85.27 seconds, including block, denied sharing, unblock, a distinct incoming invitation and encrypted sharing/readback in the same client session. Its disposable host was removed afterward.

Facebook imports now stream bounded batches, with the measured scope above. Legacy and native portable exports retain their original bounded import path. These are explicit limits, not unlimited archive capacity. Human security and accessibility reviews, the five-person usability study and independent cryptographic review remain unfinished. The selected public installation completed the final qualification below; other installations require their own acceptance checks. See [release acceptance](../docs/ENCRYPTION.md).

Failed attempts were counted and corrected: development-server reloads disrupted early tests, so qualification now serves an immutable built snapshot; repeated test logins reached production rate limits, so only disposable fixtures use an explicit test profile; room-version-12 creator permissions and fresh-room crypto timing required integration fixes. A browser test attempted a blob fetch forbidden by the actual CSP; it now verifies the real archive download instead. Neither the CSP nor production admission limits was weakened to make a test pass.

The later cross-home investigation counted five failed runs (one lost fixture network, two identity-comparison cancellations and two unavailable-history failures), one interrupted diagnostic run and one test command that failed before startup. The old retained fixture still contains ciphertext that its recovered browsers cannot decrypt; it has not been declared repaired. Earlier tests discarded browser storage without waiting for received keys to reach backup. The test now signs out through the app's backup confirmation before closing each context. Abrupt device loss before key backup remains a recovery risk. A locally generated SDK cancellation was observed without an application cancel action; its precise cause remains unproven. Successful fresh/recovered-account runs and the dialog fix do not establish that this cancellation has been eliminated.
